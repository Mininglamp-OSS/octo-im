# Recovering physical sessions after user-slot movement

A user-slot leader could change while an authenticated WebSocket stayed open on another node. The new leader had no logical connection entry, so a committed message could miss the recipient's live socket. This change gives physical socket owners a registry independent of user-slot ownership, and lets the new leader reconstruct its logical view.

## Contract

- Each physical owner has a random boot identity; each prepared socket has a random session identity. Only successful authentication of that exact live socket publishes an authenticated snapshot. A serialized `Auth` flag alone is not accepted as evidence. The pre-existing `Uptime` field carries a high-resolution, owner-monotonic socket birth value so an older relay that strips the appended identities still cannot authenticate a delayed CONNACK after numeric connection-ID reuse.
- `/wk/presence/snapshot/v2` returns authenticated session identity and routing metadata for at most 128 UIDs. The caller must declare a known member ID through transport CONNECT and must be the current user-slot leader for every requested UID; mixed-authority batches are rejected in full. Prepared sockets expose only domain-separated SHA-256 identity digests salted by the random owner boot ID, never their raw SessionID or legacy Uptime. These markers prevent recovery from evicting a logical session while its CONNACK is still traveling, but cannot authenticate a socket and are never published as online sessions. AES keys and IVs never leave the physical socket owner through this route. A recovered descriptor without crypto uses key material only from a forwarded descriptor for the same boot/session on the current SEND event, or from the live local socket context immediately before an encrypted client write; recovery never stores that key material.
- Recovery reads current online owners with at most four concurrent requests per 128-UID batch and processes up to four independent batches concurrently. It checks cluster version, UID authority and snapshot generation again before publishing each UID; churn or authority movement for one UID does not prevent valid peers in the batch from publishing. A cluster member marked offline makes the read incomplete because it may still own client sockets during a partition. Successful owner replies may restore known-live sessions during a partial failure, but only a complete read may evict stale sessions or prove a UID offline.
- Each recovery batch has a three-second budget, up to three attempts and an eight-slot node-local recovery bound. The distribution path applies a shorter 250 ms caller budget so cold recovery cannot hold a channel worker for seconds; periodic touches continue the full recovery in the background. Warm UIDs bypass the recovery bound. Positive readiness is cached for five seconds, complete negative snapshots for one second, and an evicted logical view invalidates the positive fast path. The 32,768-UID ready cache evicts expired and least-recently-used entries instead of clearing globally.
- Owners periodically touch each UID's current leader. Touches require a declared cluster member and carry only UIDs; the receiver pulls fresh snapshots, so replayed touches cannot authenticate a dead socket. Snapshot requests never acquire the recovery gate.
- Close and newly authenticated logical-session publication invalidate an in-flight snapshot generation before mutating the logical view. Connection lookup/removal and physical writes compare owner boot and session identities. Logical removal no longer deletes the physical connection manager's entry by numeric ID; only the socket close path owns that cleanup.
- The user leader verifies cold forwarded sessions with one lookup per distinct physical session and a 250 ms budget for the whole event batch. A complete owner snapshot that proves the session absent is rejected with `ReasonNodeNotMatch` and cached for one second. A timeout, transport failure, exhausted local budget, or fully legacy identity-less claim returns `ReasonSystemError` without entering that cache. Missing identity is unknown, not proof of absence. SEND remains fail-closed before persistence; idempotent PING and RECVACK frames continue to their existing session-aware handlers. Matching authenticated legacy logical sessions retain their socket-birth-checked fast path.
- Distribution attempts a bounded recovery before deciding whether a recipient is online. If recovery is incomplete, it still delivers to every session already known online and preserves the pre-existing offline-push decision for the remaining UIDs. There is no durable delivery outbox: live delivery remains best effort and history reconciliation is required after interruption.

## Compatibility and scope

Based on `fix/raft-orphan-learner-bugs` at `974cb382cd4123d492300275eb2992d172ff9c62`, with PR43/46/47/48 already merged. Session fields are appended to the internal connection encoding. During a rolling upgrade, identity-less CONNACK descriptors are accepted only when they match the physical socket owner's already-prepared local session; a complete but mismatched identity is rejected with an authentication-failure CONNACK. A cold legacy SEND on a new leader is temporarily unverifiable and rejected without a stale-session cache entry; this minimal compatibility policy does not guarantee uninterrupted mixed-version SEND after leader migration. Reconnection to publish a verified session or completion of the upgrade is required. No timeout-based or capability-probe-based fail-open is introduced.

The prepared-marker semantics require snapshot v2. The intermediate, unreleased v1 endpoint is not served: returning digests to a v1 reader could cause it to evict a pending logical session. Older nodes cannot serve v2 snapshots, so incomplete reads cannot evict sessions and complete failover recovery requires all IM nodes to be upgraded. No public client packet change is required.

`Conn.Uptime` retains its wire field but uses a high-resolution, owner-monotonic nanosecond value on upgraded owners, while old owners supply Unix seconds. `/connz` normalizes both units when rendering connection age and when sorting by uptime in either direction; its public age representation remains unchanged. A truly old owner's second-resolution birth value cannot provide the upgraded owner's sub-second reuse precision.

Message retries are bound to the complete owner boot and session identity. During a rolling upgrade, if either the retry record or current connection descriptor lost both appended identity fields through an old node, matching falls back to the pre-existing UID/node/connection tuple plus the high-resolution socket birth value in `Uptime`; partial identities and reused connection IDs with a different birth value still fail closed.

The cluster transport exposes only the self-declared CONNECT UID, not an authenticated caller identity, and does not provide built-in link encryption. Per-UID authority and membership checks reduce disclosure within the private, trusted cluster network; they do not stop an attacker who can impersonate a member on that network. Session fences prevent stale/mismatched connection state, not malicious cluster-peer impersonation. Both presence routes therefore still require a private trusted network and a deployment security decision. Existing send/channel distribution already carries server-decrypted payloads across this boundary; recovered-session delivery can add one more hop to the physical socket owner, where the payload is encrypted immediately before the client write. Deployments must prevent untrusted clients from reaching the cluster port and provide network-layer encryption (for example, a service-mesh mTLS or VPN boundary) when plaintext is not acceptable on that network. Request bodies are capped at 64 KiB before JSON decoding, and snapshots deliberately exclude client session crypto even inside that boundary.

The separate forwarding-recovery PR retains/reroutes events; this PR reconstructs connection authority. Both are needed to cover the original failure chain. The architecture borrows the separation of physical connections and recoverable logical state from upstream main `111bdee669e402f2c6dd0c285fbea315ea77007d`, adapted to this fork. Large-cluster recovery throughput has not been benchmarked.

## Verification

Repeated race-enabled tests cover recovery of an unchanged socket, close during an in-flight snapshot, missing owners, forged identity, stale authority, socket ID reuse, owner restart, logical-view eviction, physical-registry indexing, stale close/removal without touching the physical connection manager, and bounded/deduplicated OnSend verification. Server build and the full Go suite are run separately; full-suite failures are disclosed in the PR and are not a clean test result. There is no claim that the five-round WebSocket/failover experiment has been rerun.
